# Mess Menu, Feedback & Food-Wastage Tracker

A production-grade college mess management and food-wastage tracking application built using **Node.js**, **Express**, the native **MongoDB driver**, and **Chart.js**.

---

## Architectural & Schema Design Decisions

### 1. Why `mealLogs` Uses a MongoDB Time Series Collection
Mess operations generate sequential, timestamped logs for each served meal (breakfast, lunch, snacks, dinner). In MongoDB, a time series collection (configured with `timeField: "timestamp"`, `metaField: "mealType"`, and `granularity: "hours"`) is used because:
- **Optimized for Insert-Heavy Workloads:** Meals are logged continuously over semesters without updates to historical entries.
- **Columnar Compressed Storage:** Under the hood, MongoDB groups and stores time series documents in compressed columnar buckets rather than individual BSON documents. This drastically minimizes disk footprint and page I/O.
- **Efficient Range Querying:** Operational queries and analytics (such as weekly wastage trends or semester comparisons) filter by time windows. The internal bucketing enables MongoDB to query contiguous ranges of time orders of magnitude faster than a standard collection with a single B-tree index on date.

### 2. Embed vs. Reference Reasoning for `itemsServed`
Within each `mealLog`, `itemsServed` is stored as an **embedded snapshot array** (`[{ name: "Paneer Curry", qtyServedKg: 15.5 }, ...]`) rather than referencing IDs in the `menuItems` master catalog:
- **Historical Immutability & Audit Integrity:** The dishes served in a past meal represent a real-world snapshot. If the master menu item is later renamed, re-categorized, or removed by mess management, historical meal records must remain permanently accurate and unchanged.
- **Co-locality & Single-Read Operations:** In mess audits, staff and administrators always inspect the wastage figure (`wastageKg`) directly alongside what was actually served. Embedding ensures zero-join, single-document retrieval.
- **Atomic Logging:** Logging a meal and its complete dish breakdown occurs in a single atomic database operation.

### 3. Synthetic Seed Data Notice
> **Notice:** All data generated by `seed.js` (including 75 days of breakfast, lunch, snacks, dinner, item quantities, student reviews, and the recent 21-day wastage spike) is **purely synthetic** and simulated for testing and demonstration purposes. It does not represent actual institutional operational logs.

### 4. MongoDB Version Caveat for `$lookup` in `item-correlation`
> **Important Compatibility Note:** The `/api/analytics/item-correlation` endpoint joins student feedback with meal logs. In MongoDB, performing a `$lookup` on a **Time Series collection** requires **MongoDB 6.0 or higher** (and is most reliably supported in **MongoDB 6.3+**).
> 
> On earlier MongoDB versions (5.0–5.3), running `$lookup` on time series collections is unsupported or restricted. For this reason, `routes/analytics.js` includes an automatic, documented JavaScript 2-step join fallback that retrieves records and aggregates them in application memory if the underlying MongoDB server returns a pipeline compatibility error.

## Database Schema

```javascript
// menuItems (Standard Collection) — Master catalog for staff dropdown
{
  _id: ObjectId,
  name: "Paneer Curry",
  category: "curry"
}

// mealLogs (Time Series Collection: timeField="timestamp", metaField="mealType", granularity="hours")
{
  _id: ObjectId,
  timestamp: ISODate("2026-09-16T13:00:00Z"),
  mealType: "lunch",       // "breakfast" | "lunch" | "snacks" | "dinner"
  wastageKg: 8.4,
  itemsServed: [
    { name: "Rice", qtyServedKg: 20.0 },
    { name: "Paneer Curry", qtyServedKg: 15.0 }
  ]
}

// feedback (Standard Collection)
{
  _id: ObjectId,
  mealLogId: ObjectId("..."),  // References mealLogs._id
  rating: 4,                  // 1-5
  tags: ["loved it"],
  comment: "Great quality today",
  submittedAt: ISODate("2026-09-16T13:45:00Z")
}
```

## Getting Started

### 1. Prerequisites
- **Node.js** (v18+)
- **MongoDB Community Server** (v6.0+ recommended)

### 2. Environment Configuration
Create or verify `.env` in `mess-tracker/`:
```env
PORT=3000
MONGO_URI=mongodb://127.0.0.1:27017
DB_NAME=mess_tracker
```

### 3. Installation & Seeding
```bash
# Navigate to project directory
cd mess-tracker

# Install dependencies
npm install

# Run database seed (generates 75 days x 4 meals = 300 logs + feedback)
npm run seed
```

### 4. Running the Server
```bash
npm start
```
- Web Dashboard: [http://localhost:3000/dashboard.html](http://localhost:3000/dashboard.html)
- API Base: [http://localhost:3000/api](http://localhost:3000/api)

## API Endpoints

### Meal Logs
- `POST /api/meallogs`
  - Body: `{ "mealType": "lunch", "wastageKg": 7.5, "itemsServed": [{ "name": "Rice", "qtyServedKg": 18 }] }`
  - Validates: `mealType` in `['breakfast', 'lunch', 'snacks', 'dinner']`, `wastageKg >= 0`.
- `GET /api/meallogs?from=YYYY-MM-DD&to=YYYY-MM-DD&mealType=lunch`
  - Returns up to 500 meal logs sorted descending by timestamp.

### Feedback
- `POST /api/feedback`
  - Body: `{ "mealLogId": "64fa...", "rating": 5, "tags": ["loved it"], "comment": "Great food!" }`
  - Validates: `mealLogId` valid ObjectId, `rating` integer 1–5.

### Analytics Aggregations
- `GET /api/analytics/wastage-trend?weeks=10`
  - Groups by calendar week and meal type over the last N weeks.
- `GET /api/analytics/item-correlation`
  - `$lookup` join measuring correlation between meal type, food wastage, and student ratings.
- `GET /api/analytics/top-wasted-items`
  - `$unwind` on `itemsServed` ranking top dishes by quantity served.
- `GET /api/analytics/top-tags`
  - Frequency distribution of student feedback sentiment tags.
